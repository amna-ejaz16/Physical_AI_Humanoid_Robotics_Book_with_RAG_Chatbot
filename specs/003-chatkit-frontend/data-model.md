# Data Model: ChatKit Frontend Integration

**Feature**: 003-chatkit-frontend
**Date**: 2025-12-19
**Purpose**: Define data structures for ChatKit widget and backend communication

---

## Overview

This data model describes the entities and data flows for the ChatKit frontend widget integration. The widget acts as a UI layer that communicates with the existing RAG backend via REST API.

**Key Principle**: The frontend is stateless at the application level. ChatKit manages conversation state internally using browser localStorage.

---

## 1. Chat Message

Represents a single message in a conversation thread.

### Structure

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| `id` | string (UUID) | Yes | Unique message identifier | Auto-generated by ChatKit |
| `content` | string | Yes | Message text content | 1-4000 characters |
| `role` | enum | Yes | Message sender type | `'user'` \| `'assistant'` |
| `timestamp` | ISO 8601 string | Yes | Message creation time | Auto-generated |
| `status` | enum | Yes | Message delivery status | `'pending'` \| `'sent'` \| `'error'` |
| `metadata` | object | No | Additional message data | See Metadata structure |

### Message Metadata

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `request_id` | string | No | Backend request tracking ID |
| `sources` | string[] | No | Book content sources used for answer |
| `error_code` | string | No | Error code if status is 'error' |
| `error_message` | string | No | Human-readable error description |

### Example

```json
{
  "id": "msg_a1b2c3d4",
  "content": "What is physical AI?",
  "role": "user",
  "timestamp": "2025-12-19T10:30:45.123Z",
  "status": "sent",
  "metadata": null
}
```

```json
{
  "id": "msg_e5f6g7h8",
  "content": "Physical AI refers to artificial intelligence systems that interact with and manipulate the physical world through embodied forms such as robots...",
  "role": "assistant",
  "timestamp": "2025-12-19T10:30:48.456Z",
  "status": "sent",
  "metadata": {
    "request_id": "req_12345678",
    "sources": [
      "Chapter 1: Introduction to Physical AI",
      "Chapter 3: Embodied Intelligence",
      "Chapter 5: Sensor Integration"
    ]
  }
}
```

### State Transitions

```
Message Lifecycle:
┌─────────┐
│ pending │ → Initial state when user sends message
└────┬────┘
     │
     ├─→ ┌──────┐
     │   │ sent │ → Message successfully sent to backend
     │   └──────┘
     │
     └─→ ┌───────┐
         │ error │ → Message failed to send or backend returned error
         └───────┘
```

## 2. Chat Thread

Represents a conversation session with message history.

### Structure

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| `id` | string (UUID) | Yes | Unique thread identifier | Auto-generated by ChatKit |
| `title` | string | No | Thread title/summary | Max 100 characters, defaults to first message preview |
| `messages` | Message[] | Yes | Array of messages in thread | Ordered chronologically |
| `created_at` | ISO 8601 string | Yes | Thread creation timestamp | Auto-generated |
| `updated_at` | ISO 8601 string | Yes | Last message timestamp | Auto-updated |
| `is_active` | boolean | Yes | Whether thread is currently open | Defaults to `true` |

### Example

```json
{
  "id": "thread_abc123",
  "title": "Questions about Physical AI",
  "messages": [
    {
      "id": "msg_001",
      "content": "What is physical AI?",
      "role": "user",
      "timestamp": "2025-12-19T10:30:45.123Z",
      "status": "sent"
    },
    {
      "id": "msg_002",
      "content": "Physical AI refers to...",
      "role": "assistant",
      "timestamp": "2025-12-19T10:30:48.456Z",
      "status": "sent",
      "metadata": {
        "request_id": "req_12345678",
        "sources": ["Chapter 1", "Chapter 3"]
      }
    }
  ],
  "created_at": "2025-12-19T10:30:45.123Z",
  "updated_at": "2025-12-19T10:30:48.456Z",
  "is_active": true
}
```

## 3. Widget State

Represents the UI state of the ChatKit widget.

### Structure

| Field | Type | Required | Description | Default |
|-------|------|----------|-------------|---------|
| `is_open` | boolean | Yes | Widget expanded/collapsed state | `false` |
| `current_thread_id` | string \| null | Yes | Active thread ID | `null` (new thread) |
| `has_unread` | boolean | Yes | Unread message indicator | `false` |
| `theme` | enum | Yes | Visual theme | `'light'` \| `'dark'` |

### State Managed By ChatKit

ChatKit internally manages widget state in browser localStorage. The frontend application does not need to manage this state.

## 4. Backend Request

Data sent from ChatKit widget to the RAG backend.

### Structure

| Field | Type | Required | Description | Validation |
|-------|------|----------|-------------|------------|
| `question` | string | Yes | User's question | 1-4000 characters, non-empty |

### Example

```json
{
  "question": "What are the key components of a humanoid robot?"
}
```

## 5. Backend Response

Data returned from the RAG backend to ChatKit widget.

### Structure

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `answer` | string | Yes | AI-generated answer based on book content |
| `request_id` | string | Yes | Unique request identifier for tracking |
| `sources` | string[] | No | Book sections used to generate answer |

### Example

```json
{
  "answer": "The key components of a humanoid robot include: 1) Actuators and motors for movement, 2) Sensors for perception (cameras, LIDAR, force sensors), 3) Control systems for coordination, 4) Power systems, and 5) AI software for decision-making and learning.",
  "request_id": "req_9876543",
  "sources": [
    "Chapter 7: Humanoid Robot Architecture",
    "Chapter 9: Actuation Systems",
    "Chapter 11: Sensory Integration"
  ]
}
```

## 6. Error Response

Data structure for backend error responses.

### Structure

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `error` | string | Yes | Human-readable error message |
| `error_code` | string | Yes | Machine-readable error code |
| `request_id` | string | Yes | Request tracking identifier |
| `detail` | any | No | Additional error details (validation errors, stack trace in dev) |

### Error Codes

| Code | HTTP Status | Description | User-Facing Message |
|------|-------------|-------------|---------------------|
| `VALIDATION_ERROR` | 400 | Request validation failed | "Please check your input and try again" |
| `QUESTION_EMPTY` | 400 | Question field is empty | "Question cannot be empty" |
| `QUESTION_TOO_LONG` | 400 | Question exceeds 4000 chars | "Question is too long (max 4000 characters)" |
| `API_ERROR` | 500 | AI service (Gemini) error | "Unable to process question. Please try again" |
| `SEARCH_ERROR` | 500 | Vector search (Qdrant) error | "Search service temporarily unavailable" |
| `SERVICE_UNAVAILABLE` | 500 | Generic backend failure | "Service temporarily unavailable. Please try again later" |

### Example

```json
{
  "error": "Question exceeds maximum length of 4000 characters",
  "error_code": "QUESTION_TOO_LONG",
  "request_id": "req_error_123",
  "detail": null
}
```

## 7. Configuration Object

Frontend configuration for ChatKit widget initialization.

### Structure

| Field | Type | Required | Description | Default |
|-------|------|----------|-------------|---------|
| `backend_url` | string (URL) | Yes | RAG backend API endpoint | `http://localhost:8000/ask` |
| `domain_key` | string | Yes | Domain verification key | `'docusaurus-book-chatkit'` |
| `theme` | object | No | Visual theme configuration | `{ colorScheme: 'light' }` |
| `start_prompts` | PromptSuggestion[] | No | Suggested starter questions | See Prompt Suggestions |

### Prompt Suggestion Structure

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `label` | string | Yes | Display text for suggestion button |
| `prompt` | string | Yes | Full question text sent when clicked |
| `icon` | string | No | Icon name (from ChatKit icon set) |

### Example

```javascript
{
  backend_url: 'https://api.example.com/ask',
  domain_key: 'production-chatkit',
  theme: {
    colorScheme: 'light',
    radius: 'round',
    color: {
      accent: { primary: '#3B82F6', level: 2 }
    }
  },
  start_prompts: [
    {
      label: 'What is Physical AI?',
      prompt: 'Can you explain what physical AI means?',
      icon: 'robot'
    },
    {
      label: 'Humanoid Components',
      prompt: 'What are the main components of a humanoid robot?',
      icon: 'settings'
    },
    {
      label: 'Control Systems',
      prompt: 'How do humanoid robot control systems work?',
      icon: 'brain'
    }
  ]
}
```

## Persistence Strategy

### Local Storage (Managed by ChatKit)

ChatKit automatically persists:
- **Thread History**: All conversation threads
- **Messages**: Message content and metadata
- **Widget State**: Open/closed, current thread, user preferences

**Storage Key**: `chatkit_threads_{domain_key}`

**Retention**: Persists until user clears browser data or deletes threads via UI

### No Server-Side Persistence

The frontend does not store conversation data on the server. Each user's chat history exists only in their browser.

---

## Validation Rules

### Question Input

- **Length**: 1-4000 characters
- **Required**: Must not be empty or only whitespace
- **Sanitization**: Client-side HTML escaping (handled by ChatKit)

### Backend URL Configuration

- **Format**: Valid HTTP/HTTPS URL
- **Required**: Must be configured before widget initialization
- **Validation**: URL format validation on initialization

### Error Handling

- **Network Errors**: Retry with exponential backoff (handled by ChatKit)
- **4xx Errors**: Display user-friendly message, don't retry
- **5xx Errors**: Display error message with retry option

## Summary

This data model defines:
1. **Message structure** with metadata for tracking and attribution
2. **Thread management** for conversation history
3. **Widget state** managed by ChatKit internally
4. **Request/Response contracts** between frontend and backend
5. **Error structures** for comprehensive error handling
6. **Configuration objects** for widget customization

All data structures align with:
- ChatKit's expected formats
- Existing RAG backend API
- Spec requirements for user-friendly experience and book-based answers
